## 3. Architecture choice and state ownership

| Approach | Benefit | Cost/risk | Decision |
|---|---|---|---|
| Extend existing external store with focused commands and small feature folders | Preserves working foundation; one subscription/data source; no dependencies | Requires agreeing command and recovery contracts first | **Recommended** |
| Put every action and screen directly into `App.jsx` / the current store file | Few initial files | Tangled forms/navigation/storage; unsafe parallel edits; difficult domain checks | Reject |
| Add router/state/form packages and a backend-shaped repository framework | More generalized infrastructure | Dependency churn and abstractions before demonstrated need | Reject for this scope |

### Ownership

- **Durable store:** township, two demo profiles, preferences, facilities, complaints, append-only updates, activities, unique memberships, layout and attachment metadata.
- **App/session:** current demo view, entered/signed-out demonstration state, routes, return origins, list filters, one modal state and transient editor selection. No authentication token exists.
- **Feature form:** draft values, initial comparison baseline, validation errors, chosen `File`, command IDs and pending state. No offline draft persistence.
- **Session photo registry:** accepted files for this page lifetime, keyed by attachment ID. This is a preview cache; record truth stays in the durable store.
- **Temporary map:** schematic zoom/scroll, highlighted object and a pending focus request. It never owns a copy of report/activity data.
- **Derived selectors:** public facility condition, visible activities, participation counts, list filters and reference-removal reasons. Do not persist redundant counters or facility-state rows.

App passes the confirmed snapshot and command access into feature entry components. Keep the existing injected-store pattern; do not introduce a second saved-record store, provider hierarchy or generic event bus just to connect the shell.

For actor injection, add a small `createDemoSession(initialView)` controller in `src/app/demoSession.js` with `getSnapshot()`, `subscribe(listener)`, `getActor()` and `setView(view)`. It contains only transient persona state. `main.jsx` creates it with resident defaults before the durable store, passes `getDemoActor: session.getActor`, then initializes the chosen view once from the loaded snapshot/preferences and explicit route before rendering App. Inject both into App. App subscribes to the session rather than maintaining a competing persona state variable. Apply the same explicit-route precedence policy without reading/parsing localStorage a second time; choosing the SDP demo from a URL is still open demo navigation, never evidence of staff authority. This avoids a store-to-React circular dependency while leaving all saved records in the one durable store.

## 4. Proposed data and command contract

### 4.1 Version 2, preserving Part 1 data

Keep `STORAGE_KEY = 'kobi.demo.v1'` as the existing browser namespace. The **envelope version**, not the suffix in the key, determines schema. New envelope:

```text
{ version: 2, revision: nonnegative integer, data: DemoDataV2 }
```

`DemoDataV2` retains all current arrays/field names and adds:

- `profiles[].email`: required bounded email string; migration fills sample resident/staff addresses under `example.com` without changing IDs or names.
- `attachments[]`: `{ id, kind, file_name, mime_type, size_bytes }`; `kind` is `report` or `resolution`, MIME is JPEG/PNG/WebP, size is 1–5,000,000 bytes.
- Existing `photo_path` / `evidence_path` become `null` or `demo-attachment:<attachmentId>`. These are local references, not server paths or retrievable URLs.

Do not add persisted route/session/password fields, worker routes, generic operation logs or backend tables. Layout coordinates remain **integer tiles**, not the later world-pixel pivot coordinates.

Migration validates the original v1 shape before constructing v2. Preserve all valid edits, IDs, timestamps, preferences and references; add only the required defaults. Validate the complete v2 candidate, write it successfully, then publish it. On failure retain original bytes, show recovery and block feature writes. Malformed/unknown-future versions are never automatically replaced. Confirmed Reset demo remains the explicit destructive recovery path.

Stronger v2 validation must allow genuine v1 foundation data. In particular, its initial sample placements are simulation footprints, not verified final catalog art dimensions. Preserve them rather than changing positions during migration. The v1 loader permits some layouts that later placement commands would reject, such as overlap: migration preserves these structurally valid records and the editor identifies existing conflicts; it does not silently repair them. New placement/move commands enforce current spatial rules. Do not add a stricter load-time overlap/catalog rule that makes a supported v1 save unmigratable. Reject genuine structural corruption; do not call a recoverable version mismatch a successful migration.

### 4.2 Store interface

Retain `getSnapshot()`, `subscribe(listener)` and the current boolean `setRememberWorkspace(value)`, `setWorkspace(value)`, `reset()`, `retry()` compatibility methods. They delegate to the same mutation/recovery path; no second write implementation.

Add the following proposed interfaces:

```text
execute(command: DemoCommand): Result
retryPending(operationId: string): Result
discardPending(operationId: string): Result

Result = { data: object | null, error: null | { code, message, fields? } }
DemoCommand = { operationId, baseRevision, type, input }
createDemoStore(storage, { now, newId, getDemoActor, resolveAttachment }?)
```

`baseRevision` is captured from the committed snapshot when dispatching a new attempt, not from a stale list render. Expected record/layout versions below still protect drafts opened earlier. Store options have native defaults; tests inject a clock/ID factory/actor/file resolver. The actor callback reads current transient demo-view state, not persisted passwords or tokens.

The immutable snapshot adds `revision`, `pendingOperation: { operationId, type, baseRevision } | null`, and a transient `lastOperation: { operationId, type, entityId, revision } | null`. `lastOperation` lets the originating form finish the same success flow when a global Retry storage action completes its command. A single `completeSuccess(operation)` handler uses canonical selectors and deduplicates by operation ID. Missing/unmounted origins update data and feedback without forced navigation. This metadata is not a persisted audit ledger or a second record collection.

Pure domain helpers return `Result.data = { nextData, result, entityId, changed }` on success. `nextData` is the complete candidate; `result` is the command result in the table below. The store alone validates/writes/publishes it, then returns `{ data: result, error: null }` to callers. `changed: false` idempotent outcomes do not append history, increase revision or rewrite storage. Read-only selectors never dispatch commands.

Command actor is captured from the selected fixed demo persona at dispatch, inside the command layer. Screens do not supply a trusted role, resident ID, creator ID or township. This is consistent demo behavior, explicitly not a security boundary.

| Command type | Input fields | Confirmed result |
|---|---|---|
| `profile.prepareResident` | `displayName, email` | Fixed resident demo profile with local fields updated |
| `profile.updateName` | `displayName` | Current demo profile |
| `preferences.setRememberWorkspace` | `rememberWorkspace` | Preferences |
| `preferences.setWorkspace` | `workspace` | Preferences |
| `complaints.create` | `id, facilityId, description, attachment?` | Created/existing matching complaint |
| `complaints.transition` | `id, expectedVersion, nextStatus, note, updateId, attachment?` | Updated complaint |
| `activities.save` | `id, expectedVersion: null or integer, values` | Created/updated activity |
| `activities.cancel` | `id, expectedVersion` | Cancelled activity |
| `activities.join` / `activities.leave` | `id` | `{ joined, participant_count }` |
| `world.add` | `objectId, facilityId: string or null, assetKey, x, y, expectedRevision` | Added layout object |
| `world.move` | `objectId, x, y, expectedRevision` | Moved layout object |
| `world.remove` | `objectId, expectedRevision` | `{ objectId }` |
| `demo.reset` | none | Reset marker consumed by App |

`attachment` is validated metadata only; a matching validated session file must exist when a new attachment is submitted. `expectedRevision` for editor changes is captured when selection/preview begins; stale previews require review against the latest layout. `activities.save.values` contains only `title, description, category, instructions, facility_id, starts_at, ends_at, status`. No arbitrary field patching. New activity IDs are allocated before submission; `expectedVersion: null` means creation.

Keep the technical document's `{ data, error }` result convention. These commands are the local domain boundary; do not also build duplicate backend-style CRUD services for the same records. A future backend integration can adapt this boundary explicitly.

### 4.3 Commit, retry and cancellation rules

1. Generate operation/record/update/attachment IDs once per attempted operation, outside rendering. Retain them through retries. Capture an operation timestamp once; re-evaluate time eligibility using the clock at commit/retry.
2. Check actor/view, current committed records, field validity, expected versions, references and idempotency. Build one candidate and validate it before storage.
3. Save the full candidate envelope with `revision + 1`; only then publish data and a matching successful `lastOperation`.
4. On storage failure, leave committed records/revision unchanged and retain exactly one prepared command, its actor and base revision. Keep its form/file/preview mounted.
5. While a command awaits recovery, reject unrelated mutations with `STORAGE_PENDING`; explain Retry storage or Discard pending change. Do not replace it silently with another operation.
6. Retry reruns that command against the same base revision and current eligibility rules. If the stored bytes/revision changed externally, return `CONFLICT`, retain input and require reload/review. A retry is never a stale whole-snapshot replacement.
   If the command has become domain-invalid, such as an activity that has now started, show that specific error, retain draft input and offer return to editing/discard. Clear the pending attempt explicitly before submitting a changed operation; never retry an ineligible action until it appears successful.
7. Explicit discard clears the pending command/error, leaving committed records intact. Closing/cancelling a failed form must discard its pending command before departure.
8. A **failed Reset demo** stays owned by its open reset confirmation. Cancel/Escape discards its pending reset. A later generic Retry must never execute a reset the user cancelled.
9. A newly confirmed reset may supersede pending work because the confirmation explicitly names saved records, unsaved input and previews. Clear temporary state/files only after reset persistence succeeds.
10. Known external localStorage changes block writes and offer reload; no automatic multi-tab merge. Check stored baseline before commit and listen for `storage` changes. This is conservative conflict detection, not an atomic multi-tab collaboration guarantee. The supported workflow is one editing tab.

Use domain errors such as `VALIDATION_ERROR`, `CONFLICT`, `ACTIVITY_CLOSED`, `NOT_FOUND`, `STORAGE_PENDING`, `STORAGE_UNAVAILABLE`, plus clearly labeled demo-view equivalents for `FORBIDDEN` / `UNAUTHENTICATED`. Keep errors in English and distinguish local persistence errors from network/upload failures that cannot occur here.

## 5. Account, navigation and modal decisions

### 5.1 Demo account semantics

- Retain the existing resident and staff profile IDs. The sign-in Resident/SDP selector chooses which demo persona/view is entered; it never changes a role or creates authority.
- Sign-in validates email syntax and a nonempty password, then enters the selected simulated view. It does not verify credentials or claim a real session. The form explains this before submission.
- Create account validates trimmed display name 2–60, email syntax, nonempty password and exact confirmation match. It prepares the **existing local resident demo profile** with name/email, then enters resident view. Copy states: `Demo profile prepared. No real account was created.` No staff-creation option.
- The sample identity emails are local profile metadata. Profile email/township/role are read-only; profile Save changes edits only display name. Registration is explicitly a form demonstration that updates this browser's resident demo identity, not an account directory.
- Keep selected persona separate from route/layout. Sign-in to SDP or an explicit Enter SDP demo workspace action selects the staff persona; explicit Exit SDP demo workspace selects resident and returns to Map, preserving the existing exit behavior. A staff View on map return can retain staff persona temporarily. On common screens, actions requiring the resident persona offer a clearly labeled Switch to resident demo action before opening the resident form; they never create a resident-owned record under the staff ID. The profile workspace entry is associated with the SDP demo persona; the sign-in selector remains the explicit way to choose views. No route itself proves permission.
- Password strength rules are not specified; do not invent production password policy for a form simulation. Discard password fields on form exit/success; never log or serialize them.
- Preserve the Part 1 default: the bare URL opens the resident demo, or the remembered SDP workspace when enabled. Explicit hashes take precedence. Account pages are explicit demonstration routes, not an authentication gate.
- Sign out requires confirmation, clears temporary form/password/media/session state, resets the transient persona to resident defaults and routes to sign-in. Durable records remain. Direct links still open the labeled demo; this is not access control.
- The existing Remember demo workspace preference stays functional in Settings. Enter/Exit SDP remains explicitly labeled open demo navigation.

### 5.2 Route inventory and return context

Retain hash URLs with a small whitelist parser rather than adding a routing package:

```text
#sign-in                         #create-account
#map                             #map?facility=<id>
#reports                         #reports/new?facility=<id>
#reports/<id>                     #activities
#activities/<id>                  #profile
#settings                        #sdp
#sdp/reports                      #sdp/reports/<id>
#sdp/activities                   #sdp/activities/new
#sdp/activities/<id>/edit          #sdp/world
#design-system                   development only
```

Parse/decode safely; unknown/malformed routes show not-found recovery. Match `new` before ID detail routes. Derive SDP layout from the `sdp` prefix, not just equality with `sdp`. Nested report/activity routes keep the correct bottom-nav destination active. Account pages omit bottom nav and workspace-entry chrome.

Keep return route and list filters in session state. Back from detail restores its originating list/filter; direct deep links use a predictable fallback. View on map passes a facility ID, then highlights/scrolls/focuses the current matching object control. Missing/removed targets show a recovery message rather than selecting a different facility.

### 5.3 Dirty forms and one modal

`requestNavigation(target)` is the internal navigation path. A feature registers `{ isDirty, isPending, discard }`; all internal Back/Close/nav/workspace/sign-out actions use it. Browser hash Back/Forward uses the same guard: retain the current form, restore the accepted URL with `replaceState` while prompting, and apply an accepted destination once without adding a history loop. Test repeated Back/Forward explicitly.

Use `beforeunload` only while genuinely dirty; browsers control whether a reload/tab-close prompt appears and its text. No promise of persistent offline drafts or guaranteed mobile close interception.

App owns one active modal descriptor. A facility sheet can yield to photo preview/confirmation without unmounting its underlying form. Cancel returns to the same values/file/focus. During a save, guard the form handler, freeze a second submission and prevent navigation/closing from making an operation appear cancelled. No fabricated timeout is needed in normal demo operations; controlled pending examples belong in the development specimen/tests.

Generalize `ConfirmDialog` to receive action-specific `loadingLabel` and pending/close policy. Initially focus the least destructive action, trap Tab, restore the opener (or a stable heading/editor control if it disappeared), keep title/Close visible and put errors inside the active modal. Background map/editor input remains inert while modal.

## 6. Photos and evidence

Choose **session previews plus durable metadata**, as explicitly permitted by the existing prototype specification. Do not add IndexedDB or base64 localStorage persistence in this part.

- Exactly one optional report image; exactly one required resolution-evidence image at resolution commit.
- Accept JPEG, PNG and WebP, **maximum 5,000,000 bytes inclusive**. This plan resolves the ambiguous MB unit as decimal MB. Reject zero bytes, oversized/unsupported files and files the browser cannot decode.
- Validate MIME and decode actual content; an accepted file extension alone is insufficient. Invalid replacement preserves the previous valid selection. An older asynchronous decode must not overwrite a later selection.
- A session registry maps attachment ID to `File`. Stage a validated selection there before dispatch so the command boundary can resolve it. An image-preview hook owns its object URL, creates it for the displayed file and revokes it on replacement/unmount. No persisted `blob:` string.
- A prepared command retains its staged file while retry/discard is unresolved. Successful commit retains the registry entry for other detail screens in this page lifetime; failure does not lose it. Replacement/cancel/discard deletes only uncommitted attachment IDs; add `delete(id)` to the registry API. A committed attachment remains until sign-out/reset/page exit. Registry entries are not saved record truth.
- Label selection and details `Preview only — image will not remain after reload.` After reload, retain record/history/metadata and show `Photo preview is no longer available after reload.` No broken image or claimed uploaded proof.
- A resolved record with valid resolution metadata remains resolved after reload. This documents that an image was selected in the local demo; it is not durable evidence storage.
- Clear preview cache on successful reset and sign-out. Do not revoke a URL still needed by the active photo dialog; the display hook owns its own lifetime.
- Sample resolved-history/evidence states can use valid test fixtures and explicitly labeled sample metadata. Do not invent stock/generated proof images or add runtime media without source provenance.

## 7. Domain decisions

### Reports

- Resident My reports/details select only the fixed current resident's reports. Staff views select the pilot township. These are demo presentation rules, not privacy enforcement.
- Description is trimmed, length **10–1000**; facility must exist, be in the pilot and be reportable. New report creates `received`, version 1 and one initial update atomically.
- Same create ID + same owner/payload returns the existing record; changed payload under that ID is a conflict. A new form after success gets a new ID.
- Only **received → in_progress → resolved**. Notes are trimmed **5–1000**. Resolution requires a valid selected evidence file/metadata. No skipping/reopen/delete/reject.
- Status/version/history/evidence commit together; update IDs prevent duplicate history on retry. Stale expected version shows Reload report while retaining draft note/evidence until explicit reload/discard.
- Timeline is ordered by timestamp with deterministic insertion-order tie handling, includes actor label/note/status/evidence, and remains readable after preview loss.
- Public facility state is derived across all reports: any `in_progress` → `repairing`; else any `received` → `reported`; else `normal`. Map labels are Normal / Reported / Work in progress. No reporter text or images in the public sheet.

### Activities

- Complete valid drafts: title **5–100**, description **10–2000**, optional instructions **0–1000**, community/recycling category and park/hall/recycling pilot location. Draft means hidden, not a partially valid schema.
- New activity start must be future; end strictly after start. Native date/time inputs explicitly represent Malaysia time; parse with `+08:00`, validate calendar components, store UTC and format `en-MY`, `Asia/Kuala_Lumpur`, 12-hour am/pm. Do not let host timezone change entered meaning.
- Check clock on actions and when foregrounded/refreshed. While details remain visible, schedule a boundary refresh so a start time disables stale actions. This is client-clock demo behavior, not trusted server time.
- Staff create draft/published, publish a draft, edit before start, preview, or cancel. Published edits remain published; no unpublish. Started core details and cancelled records are read-only. Cancellation is terminal, uses expected version and preserves memberships; it may still mark a started event cancelled, but cannot reopen join/leave eligibility.
- Draft preview can show unsaved values without writing; it is labeled and has no participation action. Returning from preview preserves dirty state and selected fields.
- Resident lists exclude drafts, retain cancellations, sort future activities first (ascending start), then started/past activities (descending start), with deterministic ID tie breaks.
- Join requires published and `now < starts_at`; leave requires own membership and `now < starts_at`, including cancelled events. At the exact start both are closed. Unique `(activity_id, user_id)` membership makes repeats idempotent; derive counts from rows.
- Joined filter includes own memberships even if the event started or was cancelled. Show participant count and own joined state, never a resident-name list.
- Fresh initialization/reset seeds a future activity relative to one captured clock instant. Migration/reload never moves saved dates forward. Keep the no-argument fixture factory deterministic; allow an explicit seed timestamp for live reset/testing.

### Temporary map and editor

- Use a simple **32×24 logical tile schematic** with an accessible object/facility button list. The diagram is not pixel artwork. A noninteractive SVG/CSS diagram avoids tiny scaled controls; buttons remain at least 44 px.
- Provide meaningful schematic Zoom in/out and Reset view; clamp zoom to 1–3 in 0.25 steps. The viewport scrolls internally; reset restores zoom/scroll, and focus requests center the corresponding rectangle. No inert camera controls or page overflow.
- Facility list buttons open the same React sheet later used by sprites. House/tree use object ID for basic information and no report action. Multiple visible activities at one location open an explicit choice list.
- Keep existing `lamp-01`, `bench-01`, etc. Historical uppercase example IDs are not a reason to rename persisted relationships. Resolve facility → current layout placement at focus time, so moves do not stale copied coordinates.
- Editor modes are explicit: `view`, `select`, `placing`, `moving`. Use native integer X/Y fields plus schematic ghost; Part 2 does not require drag-object or worker-path code.
- Catalog is house/hall/park/lamp/bench/tree/recycling, using existing icons/live names and `Artwork pending` placeholders. No unproduced PNG paths.
- Freeze provisional simulation footprints: house 3×3; every other catalog item 1×1, matching the existing facility placements. This is intentionally not final artwork metadata. Revisit with actual asset dimensions in Part 4 before world integration.
- All placements have unique object IDs. House/tree are decorative with `facilityId: null`; other five types create a unique corresponding facility atomically. Preserve existing reportability; new nondecorative facilities are reportable, and only park/hall/recycling are activity locations.
- Check integer positions, full rectangle within `[0,32) × [0,24)`, and no overlap. During move exclude the moved object's original rectangle; preserve object/facility IDs. Preview/cancel never writes.
- Remove requires confirmation. Block removal if **any** report or activity references its facility, including resolved reports and draft/cancelled activities. Remove unreferenced facility+object together; clear stale selection/panel/focus after success.
- Exit editor discards uncommitted placement/move preview; previously saved changes remain. Failed placement/move stays visible for recovery. Reset restores coherent records/layout and clears transient selection only after persistence succeeds.
- Bounds/overlap/reference validation proves the **temporary layout simulation only**. Real art footprint/pivot, hit areas, camera dragging and worker access routes are later Parts 4–7 checks; do not claim a simulated placement is ready for the final world.
